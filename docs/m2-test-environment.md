# M2 isolated commerce test environment (Milestone 2.1)

Local-only environment for testing commerce (standard + personalised products) without
touching the development database, its orders or its customers.

| | Original development | **M2 test** |
|---|---|---|
| PostgreSQL | 127.0.0.1:5432, database `jemsutra`, data `apps/backend/.pgdata` | **127.0.0.1:5433**, database **`jemsutra_m2test`**, data **`apps/backend/.pgdata-m2test`** |
| Backend | :9000 (`npm run dev`) | **127.0.0.1:9001** (`npm run m2test -- backend`) |
| Storefront | :3000 (`npm run dev`), build folder `.next` | **127.0.0.1:3001** (`npm run m2test -- storefront`), build folder **`.next-m2test`** |
| Settings | `apps/backend/.env`, `apps/storefront/.env.local` | **`apps/backend/.env.m2test`**, **`apps/storefront/.env.m2test`** (generated, git-ignored) |
| Emails | `apps/backend/.outbox` | **`apps/backend/.outbox-m2test`** (files only, never sent) |
| Publishable key / secrets | original | **separate, generated by `init` / `seed`** |
| Image service | :4100 (shared, read-only renders) | same |

The test services bind to **127.0.0.1 only**. (The original :3000/:9000/:4100 dev servers
listen on all interfaces; that is unchanged and out of scope for M2.1.)

## Commands

```bash
npm run m2test -- init         # once: create the two .env.m2test files with new secrets
npm run m2test -- db           # terminal 1: separate PostgreSQL on 5433 (Ctrl+C stops it cleanly)
npm run m2test -- mark         # once, on the fresh database: set the M2 sentinel label
npm run m2test -- migrate      # Medusa migrations - test database only
npm run m2test -- seed         # region, delivery, payment, code-catalog designs; writes the test key
npm run m2test -- designs      # copy JS0001-JS0003 definitions (JSON only) from the dev database
npm run m2test -- backend      # terminal 2: test backend on 127.0.0.1:9001
npm run m2test -- storefront   # terminal 3: test storefront on 127.0.0.1:3001
npm run m2test -- preflight    # run every isolation check, change nothing
npm run m2test -- verify       # read-only side-by-side comparison of both databases
```

**Stop:** Ctrl+C in each terminal (storefront, backend, then database).
If a process was started in the background, find it by port and stop it:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 3001,9001 | ForEach-Object { Stop-Process -Id $_.OwningProcess }
```

Stop the database with Ctrl+C where possible (clean shutdown). Never stop :5432 / :9000 / :3000 for M2 work.

## Fail-closed isolation (how the original database is protected)

1. **Settings check** before every database command: `DATABASE_URL` must be loopback, port
   5433, database `jemsutra_m2test`, and different from the original; `DB_NAME`, `STORE_URL`
   (:3001) and `OUTBOX_DIR` must be the test values; secrets must differ from the original.
2. **No inheritance:** Medusa always loads `apps/backend/.env` and fills in any missing key, so
   the test file must define **every** key of `.env`, otherwise the launcher refuses. Child
   processes get a rebuilt environment: original database, secret and storefront variables are
   removed, then only the test values are set.
3. **Server identity check** (read-only transaction): the server must report port 5433,
   database `jemsutra_m2test`, data directory `apps/backend/.pgdata-m2test`, a loopback
   address, and the sentinel comment `thegemsutra:m2-commerce-test:isolated` (set once by
   `mark`, only on an empty database). The original database has no sentinel, so even a
   mis-edited settings file pointing at 5432 is refused.
4. **Script-level guard:** `src/scripts/m2test-sync-designs.ts` repeats the URL + server +
   sentinel check itself and refuses to run against anything else.
5. **Seed once:** `seed` refuses if the test database already has a region.
6. **Folder-name guards:** `PG_DATA_DIR`, `OUTBOX_DIR` and `NEXT_DIST_DIR` only accept
   `.pgdata[-name]`, `.outbox[-name]`, `.next[-name]`; defaults are unchanged.

## Rollback

The original database is never written by M2.1. To remove the test environment completely:

1. Stop the test storefront, test backend and test database (above).
2. Delete `apps/backend/.pgdata-m2test`, `apps/backend/.outbox-m2test`,
   `apps/storefront/.next-m2test`, `apps/backend/.env.m2test`, `apps/storefront/.env.m2test`
   (all git-ignored).
3. Optionally revert the M2.1 code changes (all defaults are backward-compatible, so they can
   also stay).

To start again from empty, delete `.pgdata-m2test` and run `db`, `mark`, `migrate`, `seed`,
`designs`.

## Known configuration notes

- The image service is shared: it renders personalised images from the **development**
  backend's design definitions. The test database holds identical copies (`designs` verifies
  this), but if designs are edited in one environment only, renders follow the dev backend.
- Both backends run `medusa develop` in `apps/backend`: editing backend files restarts both.
- Next.js adds `.next-m2test/types` to `apps/storefront/tsconfig.json` when the test storefront
  starts (framework-generated; harmless).
- The embedded PostgreSQL has no `pg_dump`; no backup was needed because nothing writes to
  `jemsutra`. Before any future change to the development database, create a consistent dump
  with a PostgreSQL client that provides `pg_dump` (never copy a running data folder).

## M2.2 cart & pricing security (fixed and tested in the test environment)

**Status:** 18 bypasses confirmed against the TEST database (before), all refused after the
fix (28/28 security tests pass; 13/13 direct workflow hook checks pass). Never tested against
the development database.

**How it is enforced** (`apps/backend/src/lib/cart-security.ts` is the single policy):
- Request guards (`src/api/middlewares.ts`) on `POST /store/carts`, `POST /store/carts/:id`,
  `POST /store/carts/:id/line-items`, `POST` + `DELETE /store/carts/:id/line-items/:line_id`.
- Workflow hooks (`src/workflows/hooks/cart-security.ts`) on addToCart, updateLineItemInCart,
  createCart, updateCart and completeCart - they apply whatever starts the workflow.
- Checkout: inside Medusa's cart lock, every personalised line is rebuilt from its stored design
  and the current published definition; variant, quantity (1), price and all trusted metadata
  must match exactly or no order is created.
- Designer route: `replace_line_id` must be a personalised line of the same cart; each line gets
  a server `line_ref` so identical designs stay separate lines.
- Standard products: normal variants and quantities; client line metadata only from an explicit
  allowlist (empty); client cart metadata refused (it is copied onto the order).

Commands: `npm run m2test -- fixtures` (once), `npm run m2test -- security`,
`npm run m2test -- hooks`.

**Test suites:** `security` = 28 HTTP integration tests against the test backend and test
database (routes + middleware + hooks + designer route + checkout, including direct
test-DB corruption to exercise the checkout check). `hooks` = 13 checks that call Medusa's
workflows directly with no HTTP route, proving the workflow hooks on their own. They overlap
by design for add/update/create/update-cart (two layers); only `security` covers checkout,
cross-cart deletion, `replace_line_id` and concurrency.

**Known limitations (not production-proven):**
- Checkout serialisation relies on Medusa's cart lock. The default locking provider is
  **in-process memory**: it is only effective while ONE backend process serves the store. With
  several backend instances or workers, configure a shared locking provider (e.g. Redis) and
  re-run the concurrency test before relying on it. Not tested with multiple instances.
- Every completion path found runs `completeCartWorkflow` (store `/complete` route and the
  payment-webhook `completeCartAfterPaymentStep`), so the checkout check applies to both; the
  webhook path is covered by code inspection only (no payment provider with webhooks yet).
- Promotions, customer transfer and shipping-method routes don't write line data and were not
  reviewed for pricing abuse. Admin routes (order edits, draft orders) are trusted and outside
  this policy.
- A design whose options or prices change after it was added to a cart makes that line stale:
  checkout refuses it (by design); the storefront currently shows a generic error.
- The 14 legacy per-metal variants still exist in the development database; they are now
  refused by every cart path but are not removed.

### Original finding (for the record)

**Assumption that breaks:** personalised lines are only ever created by
`POST /store/designs/:style/cart-items`, which re-prices on the server and writes the trusted
line metadata (`design`, `design_summary`, `engraving_lines`, `price_lines`, `image_url`).
Medusa's standard store endpoints are still open (there is no `src/api/middlewares.ts`) and
accept client-supplied variants **and metadata** (validators in
`@medusajs/medusa/dist/api/store/carts/validators.js`):

| Endpoint | Client may send | Risk |
|---|---|---|
| `POST /store/carts` | `items[]: { variant_id, quantity, metadata }` | Personalised variant without server pricing / with forged design metadata |
| `POST /store/carts/:id/line-items` | `variant_id, quantity, metadata` | Same: e.g. JS0003 "Made to order" (base price) or a legacy per-metal variant (`JS0001-14KR`…, development DB only) with forged `design_summary` / `engraving_lines` |
| `POST /store/carts/:id/line-items/:line_id` | `quantity, metadata` | **Rewrite a server-priced personalised line's design/engraving after pricing** (e.g. silver price, gold on the workshop sheet); change quantity |

`unit_price` is not accepted by these validators (good), but prices are still wrong where the
variant's base price is used, and the workshop sheet / emails trust line metadata.

Also to verify: `replace_line_id` on the design route deletes a line by id - confirm the line
must belong to `cart_id`.

### Proposed M2.2 fix
1. `apps/backend/src/api/middlewares.ts` with request middlewares on the three endpoints:
   - resolve each `variant_id` → product; refuse (400) if `product.metadata.personalised` is
     true ("Personalised items must be added through the designer");
   - strip or refuse client `metadata` on standard lines (allow-list of harmless keys only);
   - on line updates: refuse any `metadata` change and any quantity change ≠ 1 for lines
     carrying `metadata.style_code`; allow quantity changes for standard lines.
2. Design route: verify `replace_line_id` belongs to `cart_id`.
3. Defence in depth at checkout: before `cart.complete`, re-validate every personalised line
   (re-price from `metadata.design` and compare with `unit_price` and the stored summary);
   refuse on mismatch.
4. Separately (needs approval, development DB): archive the 14 legacy per-metal variants.

### M2.2 regression tests (test database only, dummy identities, `@example.test`)
Read-only / unit:
- middleware logic with mocked product lookups (personalised vs standard, metadata rules);
- design pricing unchanged (engine tests, 13 ring golden cases, price route Rs 139,800 / 12,900).

Writes to the TEST database only:
- `POST /store/carts` with a personalised variant in `items` → refused;
- add personalised variant via `/line-items` → refused; with forged metadata → refused;
- update a designer-created line's metadata → refused; quantity 2 → refused; quantity 0 (remove) → allowed;
- designer route still adds, modifies (`replace_line_id`) and prices correctly;
- `replace_line_id` from another cart → refused;
- checkout re-validation rejects a tampered personalised line;
- emails land only in `.outbox-m2test`, addressed to `@example.test`.
